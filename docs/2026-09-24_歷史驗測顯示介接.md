# 歷史驗測顯示 — IVT 智慧網路中牆介接說明

> 對象:IM adapter(`10.194.87.115:8012`)維護者
> 目的:共通性測試平台要求「顯示某一次歷史驗測結果」時,讓 IVT 中牆切換到那一筆
> 版本:2026-09-24(IVT 端已完成並上線)

---

## 1. 這件事的全貌

```
共通性測試平台
   │ ① POST /autoTest/test/notifyHisShow   body: ["<runningId>", …]
   ▼
IM adapter (:8012)
   │ ② 把 runningId 換成 run_id,轉發:POST {IVT}/api/field-tests/history/  body: ["<run_id>", …]
   ▼
IVT 後端
   │ ③ 判斷屬於室內或室外 → 記住「這面牆要顯示這一筆」
   ▼
IVT 中牆(每 1~15 秒輪詢自己的後端)
   │ ④ 用 run_id 去 Performance_tester(:8011)拉那次的資料
   ▼
畫面換成那一次的路徑圖、進度、吞吐量對照
```

**中牆沒有推播通道**,它固定輪詢自己的後端問「現在該顯示哪一筆」。
所以「通知中牆」實際上就是「把 run_id 寫進 IVT 後端」。

---

## 2. 需要 adapter 做的事(只有一件)

在 `POST /autoTest/test/notifyHisShow` 的處理裡,把平台送來的 ID **換成
Performance_tester 的 `run_id`** 之後轉發一份給 IVT:

```python
@app.post("/autoTest/test/notifyHisShow")
def notify_his_show(body: list = Body(...)):
    ...                                   # 原本的記錄邏輯保留
    try:
        httpx.post(NOTIFY_FORWARD_URL, json=body, timeout=3)   # body 原樣轉發即可
    except Exception:
        pass                              # 轉發失敗不影響平台,仍回 200
    return Response(status_code=200)
```

> **不需要在 adapter 換算 ID。** 平台送的 `runningId` 是 adapter 自己發的,
> Performance_tester 不認得,但 IVT 會去讀 adapter 的 `/autoTest/history`
> (那份清單 `runId` 與 `runningId` 兩個欄位都有)自己換算 ——
> 所以 **`runningId` 與 `run_id` 兩種都收**,body 原樣轉過來就好。
> 兩種都認不得的 ID 會放進回應的 `unknown` 並略過。

```
NOTIFY_FORWARD_URL = http://<IVT 主機>:38080/api/field-tests/history/
# 目前實機:http://10.194.87.120:38080/api/field-tests/history/
```

> adapter 目前已具備 `NOTIFY_FORWARD_URL` 的轉發能力(見其 OpenAPI 說明),**但尚未設定**。
> 設定之後即時生效;未設定時 IVT 會退回輪詢(見第 5 節),延遲較長且牆面頁面必須開著。

## 3. IVT 端點規格

Base:`http://<IVT 主機>:38080/api/field-tests`(目前實機 `10.194.87.120:38080`)

> ⚠ 對外埠是 **38080** 不是 8080 —— 2026-09-22 起 nginx 換到 38080,8080 已關閉。
認證:預設免認證(內網服務對打)。IVT 若設了 `FIELD_TEST_NOTIFY_TOKEN`,寫入類請求需帶 `X-Notify-Token: <token>`。

### 3.1 通知顯示歷史紀錄

```
POST /api/field-tests/history/
Content-Type: application/json

["62222e39-5f19-4d25-8947-1a9b3a0b8f18"]
```

**body 形狀**:與 `notifyHisShow` 完全相同(字串陣列)。為方便相容也接受
`{"runningIds": [...]}`、`{"running_ids": [...]}`、`{"running_id": "..."}`、單一字串。

**ID 一律是 Performance_tester 的 `run_id`**(UUID 36 碼,例如
`62222e39-5f19-4d25-8947-1a9b3a0b8f18`)。平台的 `runningId`(12 碼,例如
`b967cd21d39b`)請 adapter 先換算 —— IVT 這端不做換算。

**一次多筆**:依每一筆所屬的環境分給室內 / 室外兩面牆(室內、室外各自一面);
同一面牆被指定多筆時取 `created` 最新的那一筆。

**回應**(平台不解析,僅供對帳除錯):

```jsonc
200 OK
{ "pinned": { "indoor": "62222e39-5f19-4d25-8947-1a9b3a0b8f18" }, "unknown": [] }

404 Not Found            // 沒有任何一筆對得上室內 / 室外的方案
{ "detail": "沒有一筆對得上室內 / 室外的方案", "unknown": ["doesnotexist999"] }

422 Unprocessable        // body 不是一串 ID
{ "detail": "body 要是一串 runningId" }

403 Forbidden            // 有設 token 但沒帶對
{ "detail": "X-Notify-Token 不對" }
```

認不得的 ID 會放進 `unknown`,不影響同一次請求裡其他有效的 ID。

### 3.2 查目前顯示中的紀錄

```
GET /api/field-tests/history/
200 { "pinned": { "indoor": "62222e39-…", "outdoor": "…" } }     // 空物件 = 沒有指定,牆面顯示最新一次
```

### 3.3 取消指定(回到即時 / 最新)

```
DELETE /api/field-tests/history/              // 兩面牆都清
DELETE /api/field-tests/history/?scenario=indoor   // 只清室內(indoor | outdoor)
200 { "pinned": { … } }                       // 清完之後剩下的指定
```

### 3.4 驗測紀錄清單(挑「要顯示哪一次」用)

```
GET /api/field-tests/records/?scenario=indoor      // scenario 可省略 = 全部
200
{
  "runs": [
    {
      "runId": "62222e39-5f19-4d25-8947-1a9b3a0b8f18",
      "status": "done",                 // done | error | aborted | running | ready
      "created": 1790148556.3,          // epoch 秒
      "phases": { "優化前": 53, "優化後": 54 },   // 各階段的樣本筆數
      "bothPasses": true,               // 兩趟都有足夠資料(false 的話牆上會有半邊是空的)
      "environmentId": "a74cec96-…",
      "pinned": false                   // 是不是目前顯示中的那一筆
    }
  ],
  "pinned": { "indoor": "…" }
}
```

新的在前面。建議挑 `bothPasses: true` 的紀錄,否則牆上「啟用前後」的對照會有一半是「—」。

## 4. 牆面的顯示規則

IVT 後端決定「這面牆顯示哪一筆」的順序:

1. **有正在執行(`running` / `ready`)的驗測** → 顯示它,**並清掉歷史指定**
2. 否則有歷史指定 → 顯示那一筆
3. 否則 → 最新一次(偏好兩趟都完整的)

也就是說:

- 指定之後會一直停在那一筆,直到**下一次通知**、**平台開跑新的驗測**、或**呼叫 DELETE**
- 新驗測開跑會自動回到即時;那一輪跑完之後牆面停在**新的那一筆**,不會跳回歷史
- 指定的紀錄若被平台刪掉、或不屬於該面牆,IVT 會自動清掉並退回「最新一次」

**不受影響的部分**:牆面左側「即時狀態」(攝影機、飛行 / 行駛狀態、通訊品質)永遠顯示當下的遙測,與歷史指定無關。

**延遲**:

| 路徑 | 從通知到畫面換好 |
|---|---|
| adapter 轉發(建議) | ≤ 15 秒(牆面輪詢週期) |
| IVT 輪詢(備援) | ≤ 20 秒(adapter 輪詢 5 秒 + 牆面輪詢 15 秒),且牆面頁面必須開著 |

## 5. 備援:IVT 主動輪詢 adapter

在 `NOTIFY_FORWARD_URL` 設定好之前(或轉發失敗時),IVT 會在牆面輪詢時順便讀:

```
GET {adapter}/autoTest/history/notified
{ "notified": [ { "id": "62222e39-…", "notified_at": 1790148753.6, "count": 1 }, … ] }
```

- 以 **`notified_at` 是否變動**判斷是不是新的通知(所以同一筆重複通知也抓得到)
- 後端重啟後的第一次只記錄、不切畫面(避免跳到很久以前的通知)
- 清單裡的 `id` 同樣**必須是 `run_id`**;若是 adapter 自己的 `runningId`,IVT 認不得會略過

**請保留這支端點與 `notified_at` / `count` 欄位。**

## 6. 驗收步驟

```bash
# 1. 看有哪些紀錄可挑
curl "http://<IVT>:38080/api/field-tests/records/?scenario=indoor"

# 2. 模擬平台通知(從任何一台打得到 adapter 的機器;這裡直接給 run_id)
curl -X POST http://10.194.87.115:8012/autoTest/test/notifyHisShow \
     -H 'Content-Type: application/json' \
     -d '["62222e39-5f19-4d25-8947-1a9b3a0b8f18"]'
# → 200(無 body)

# 3. 確認 IVT 收到
curl "http://<IVT>:38080/api/field-tests/history/"
# → {"pinned":{"indoor":"62222e39-…"}}

# 4. 看牆面:右上「測試項目」變成「09/23 15:29 · 62222e39」,
#    路徑圖與上下兩張折線圖換成那一次的資料

# 5. 回到最新
curl -X DELETE "http://<IVT>:38080/api/field-tests/history/?scenario=indoor"
```

## 7. 已知注意事項

| 項目 | 說明 |
|---|---|
| ID 型別 | 平台送的 `runningId` 只有「經 adapter 驅動」的紀錄才有(目前 47 筆中 6 筆);其餘是直接在 Performance_tester 上跑的,只有 `run_id`。IVT 只收 `run_id`,換算請在 adapter 完成。 |
| 不完整的紀錄 | `status` 非 `done`、或只有單趟資料的紀錄仍可顯示,但牆上對照圖會有一半是「—」。 |
| adapter 重啟 | adapter 的通知狀態若在重啟後消失,且當下 IVT 沒有輪詢到,該次通知會漏掉 —— 這也是建議改用轉發的原因。 |
| 情境判斷 | IVT 依紀錄的 `meta.environment_id` 對應到室內 / 室外方案;兩者都對不到就歸類為 `unknown`。 |
